# Memnest Productization Plan

Goal: bring memnest to commercial-grade memory hygiene. Six tasks, ordered by
dependency. Each task is sized for a single cheap-model implementation pass
(Sonnet-class), with exact files, exact changes, acceptance criteria, and a
verification recipe the implementer must run and paste output for.

Ground rules for every task:

- Rust work happens in `core/`. Run `cargo check` and `cargo test` in
  `/home/shell/memnest/core` before claiming done. Zero errors required.
- Never touch the production instance (port 3111, `~/.memnest`). Verify against
  a throwaway dev instance:
  `./target/release/memnest --host 127.0.0.1 --port 3999 --data-dir /tmp/memnest-dev`
  (delete `/tmp/memnest-dev` between runs).
- No pushes. Local commits only, one commit per task, message
  `feat(core): <task title>`.
- Do not refactor unrelated code. Smallest diff that satisfies acceptance.
- Existing behavior must not change unless the task says so. `_superseded`,
  reserved buckets (`root`/`default`/`global`), and encryption paths are
  off-limits unless named.

Status legend: [ ] todo, [x] done, [~] in progress.

## [x] T0. Configurable AutoLog TTL (DONE 2026-07-13, by parent agent)

`MEMNEST_TTL_AUTOLOG_DAYS` env: `0`/`off`/`unlimited` → never expire; positive
int → that many days; unset/invalid → 30 (old default). Implemented in
`core/src/lifecycle/mod.rs` (`autolog_ttl_days()` + `ttl_days_for`).
Local deployment pins `Environment=MEMNEST_TTL_AUTOLOG_DAYS=0` in
`~/.config/systemd/user/memnest.service`.

Verified: service restarted with new binary, prune window passed, root chunk
count unchanged (17,092), no `daily TTL pruned` journal line.

## [x] T1. Lifecycle observability (last prune visible)

Why: on 2026-07-11 the TTL loop silently deleted 4,931 chunks. Users must be
able to see when the pruner last ran, what it deleted, and whether it failed.

Files:

- `core/src/lifecycle/mod.rs`
- `core/src/server/api.rs` (`HealthResponse`, `StatsResponse`, handlers)
- `core/src/lib.rs` or wherever `MemorySystem` is defined (add state)

Changes:

1. Add to `MemorySystem` a `lifecycle_status: RwLock<LifecycleStatus>` where
   `LifecycleStatus { last_run: Option<DateTime<Utc>>, last_deleted: usize,
   last_error: Option<String>, ttl_autolog_days: Option<i64> }`.
2. `prune_expired` updates it on every run (success and failure paths).
   `spawn_periodic_lifecycle`'s error arm records `last_error`.
3. `/health` response gains `lifecycle: { last_run, last_deleted, last_error,
   ttl_autolog_days, enabled }` (enabled = config.enable_lifecycle).
4. Log line for a zero-delete run upgraded from `debug!` to `info!`
   (`"daily TTL: nothing to prune"`), so absence of logs is meaningful.

Acceptance:

- `curl :3999/health` shows the lifecycle block; before first run `last_run`
  is null; after the 120s startup prune it is a timestamp.
- Simulated failure (unit test calling the status update on Err) records
  `last_error`.
- `cargo test` passes; add one unit test for `LifecycleStatus` update.

Verify recipe (paste output):

```
cargo check 2>&1 | tail -3
cargo test lifecycle 2>&1 | tail -5
./target/release/memnest --host 127.0.0.1 --port 3999 --data-dir /tmp/memnest-dev &
sleep 130 && curl -s localhost:3999/health | python3 -m json.tool
```

## [x] T2. Health report + cleanup recommendation (/stats extension)

Why: "when should I clean up" must be answered by the system, not by the user
running SQL. Depends on T1 (reuses lifecycle status).

Files: `core/src/server/api.rs` (`StatsResponse`, `stats` handler),
`core/src/storage/mod.rs` (new aggregate queries).

Changes:

1. Extend `/stats` with:
   - `collections`: per-project `{ chunks, text_bytes }` (extend existing
     `collection_stats`).
   - `age_buckets` for `root`: counts older than 30/90/180 days.
   - `disk`: bytes of `memory.db`, `text_index/`, `vectors/` (walk data_dir).
   - `recommendations`: array of strings, generated by fixed thresholds:
     root > 50,000 chunks; disk total > 2 GiB; any project with > 500
     near-duplicate suspects is out of scope (no embedding scan here — keep it
     cheap and deterministic).
2. Thresholds live in one `const` block with comments, not scattered.

Acceptance:

- `curl :3999/stats` returns the new fields on an empty dev instance without
  panicking (zeros, empty recommendations).
- With `MEMNEST_DATA_DIR` pointed at a copy of real data, numbers are plausible
  (chunks match `select count(*)`).
- `cargo test` passes; unit test for threshold → recommendation mapping.

## [x] T3. Prune dry-run + audit log

Why: nobody clicks a mass-delete without a preview. `/prune` already exists;
it needs `dry_run` and an audit trail.

Files: `core/src/server/api.rs` (`PruneRequest`, `PruneResponse`, `prune`
handler).

Changes:

1. `PruneRequest` gains `dry_run: bool` (default false, serde default).
2. When `dry_run`, compute the victim set exactly as today but delete nothing;
   respond `{ dry_run: true, would_delete: <count>, sample: [up to 20 of
   {id, project, created_at, first 80 chars}] }`.
3. Every real prune (and TTL prune in lifecycle) appends one JSON line to
   `<data_dir>/audit.log`: `{ts, source: "api"|"ttl", deleted, filters}`.
   Failure to write audit is a warn, never blocks the prune.

Acceptance:

- Dry-run on dev instance with seeded chunks returns correct count and deletes
  nothing (verify by re-query).
- Real prune writes an audit line; TTL prune writes `source:"ttl"`.
- `cargo test` passes.

## [x] T4. Pin (exempt a chunk from any automatic expiry)

Why: "remember this one forever" must be possible on auto_log without copying
it to another bucket by hand.

Files: `core/src/models.rs` (chunk metadata), `core/src/storage/mod.rs`
(persist/read flag), `core/src/lifecycle/mod.rs` (skip pinned),
`core/src/server/api.rs` + `core/src/server/mcp.rs` (accept `pinned` in add
and update).

Changes:

1. `ChunkMetadata` gains `#[serde(default)] pinned: bool`. Old rows without the
   field deserialize as false (verify serde default works with stored JSON).
2. `prune_expired` skips pinned chunks regardless of TTL.
3. `/add` and `/update` accept `pinned`; `memory_update` MCP schema exposes it.
4. `/prune` also skips pinned unless request sets `include_pinned: true`.

Acceptance:

- Seed a chunk with `created_at` forced old (insert via API then UPDATE the
  sqlite row's created_at in the test), set TTL to 1 day via env on the dev
  instance, confirm prune deletes an unpinned twin but keeps the pinned one.
- Old DB rows still load (backward-compat test: insert metadata JSON without
  `pinned` directly, read it back).
- `cargo test` passes.

## [x] T5. Soft-delete trash (recoverable deletes)

Why: today `/delete` and `/prune` are instant and permanent; recovery is a
manual DB backup. Commercial software needs an undo window.

Files: `core/src/server/api.rs`, `core/src/storage/mod.rs`,
`core/src/lifecycle/mod.rs`.

Changes:

1. `/delete` and `/prune` (non-dry-run) move chunks to project `_trash`
   instead of deleting: store `original_project` and `trashed_at` in metadata,
   remove from text/vector indexes (so search never surfaces trash).
2. New endpoint `POST /restore { ids }`: moves back to `original_project`,
   re-indexes (re-embed + text index add).
3. Lifecycle purges `_trash` rows older than 30 days (hard delete). This purge
   respects nothing else — trash is trash.
4. `_trash` joins the reserved-bucket lists (excluded from collections_list,
   search-all, manual writes).

Acceptance:

- Delete → chunk invisible to search, visible via direct DB in `_trash`.
- Restore → searchable again in original project with same id.
- Trash row older than 30d is purged by lifecycle; younger survives.
- `cargo test` passes; audit lines (T3) written for trash-purge with
  `source:"trash_gc"`.

## [x] T6. Archive before hard delete

Why: even with unlimited TTL locally, the product default (30d) must not mean
amnesia. Anything hard-deleted by lifecycle (TTL prune, trash GC) is appended
to a monthly JSONL archive first; recovery/搜索 over archives is out of scope.

Files: `core/src/lifecycle/mod.rs` (both prune paths), small helper module.

Changes:

1. Before hard-deleting a chunk, append full chunk JSON (document + metadata +
   created_at) to `<data_dir>/archive/YYYY-MM.jsonl`.
2. Append failures: warn + skip archive, still delete (availability over
   completeness), but count failures in lifecycle status (T1).
3. `MEMNEST_ARCHIVE=0` disables archiving.

Acceptance:

- Dev instance with 1-day TTL: expired chunk appears in
  `/tmp/memnest-dev/archive/<month>.jsonl` before disappearing from DB.
- `MEMNEST_ARCHIVE=0` produces no archive file.
- `cargo test` passes.

## Execution protocol (parent agent)

1. One task per subagent run, model `claude-bridge/claude-sonnet-4-6`, fresh
   context, this file section as the spec. Never give a subagent more than one
   task.
2. Subagent must paste: `cargo check` tail, `cargo test` tail, and the verify
   recipe output. No pasted output → not done.
3. Parent verifies independently: read the diff, run `cargo test`, run the
   task's curl checks against a dev instance, then mark the checkbox here and
   commit.
4. Any deviation from spec (extra refactors, new deps, touched prod data dir)
   → reject and re-run with narrower instructions.
5. Production deploy (copy binary + restart systemd unit) happens only after
   T1-T3 land together, then again after T4-T6. Stop service before `cp`
   (binary is busy while running).
6. Push to GitHub only on explicit user approval.
