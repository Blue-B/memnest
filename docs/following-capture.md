# 검색된 질문에서 후속 답변 원문으로 이동하기

## 구현 범위

검색된 기록이 사용자 발언이면, 같은 프로젝트·세션·수집 출처·작업 경로에서
뒤에 수집된 AI 답변을 `following_id`로 안내한다. 그 ID를 기존 `memory_get`으로
읽으면 된다. 본문이나 결과를 더 붙이거나 기존 검색 순서를 바꾸지 않는다.

- 검색 한 번에 후속 출처 링크는 최대 1개다. 추가 모델 호출이나 임베딩은 없다.
- 기존 주변 기록 조회를 재사용해 뒤의 기록 최대 5개만 살핀다.
- 확인한 범위에서 사용자 발언, 알 수 없는 역할, 민감 표시, 여러 조각으로 나뉜
  발언 또는 요청과 다른 분류를 만나면 더 넘어가지 않는다.
- 그 경계 앞에서 마지막으로 확인한 단일 조각 AI 발언을 안내한다.
- 이미 검색 결과에 있는 출처는 중복 안내하지 않는다.
- 이름이 답변에 없어도 같은 대화의 후속 설명으로 안내할 수 있다.
- 최신순 조회와 영구 기억만 조회하는 문맥 검색에는 이 안내를 추가하지 않는다.
- HTTP는 선택 필드로, MCP와 pi는 읽을 ID와 주의 문구로 표시한다.
  예전 클라이언트는 새 필드를 무시해도 기존 검색 결과를 그대로 읽을 수 있다.

이것은 **검증된 정답 연결이 아니라 후속 수집 기록 안내**다. 기록이 없거나
삭제됐거나 다른 순서로 가져온 경우 실제 대화의 인접 관계와 다를 수 있다.
진행 보고가 마지막에 보일 수도 있다. 원문을 읽고 답이 되는지 판단해야 한다.
삭제·숨김 상태인 기록을 링크 대상으로 다시 노출하지 않는다.

## 해결하지 않는 것

이름이 없는 모든 관련 기록을 뜻으로 찾아내는 개선은 아니다. 질문이 검색되지
않거나, 다른 세션에 답이 있거나, 뒤의 다섯 기록 밖에 답이 있으면 이 안내만으로
찾을 수 없다. 질문과 답의 검증된 부모 관계를 새로 저장하지 않으며, 과거 데이터를
다시 수집하거나 별도 AI로 요약하지 않는다.

## 검증 과정과 결과

처음에는 결과에 빈자리가 있을 때 후속 답변을 별도 결과로 하나 추가했다.
기존 14개 질문에서는 통과했지만, 추가 실제 사례에서는 이미 결과가 다섯 개여서
이름 없는 후속 설명을 넣지 못했다. 그 후보는 채택하지 않았다.

최종 후보는 **본문 대신 출처 ID만 안내**하도록 줄였다. 추가 사례는 원래 사용자
질문 그대로 고정했고, 실패를 없애려고 질문을 고치거나 순위 가중치를 조정하지 않았다.

같은 격리 DB에서 기존 14개 질문과 추가 실제 질문 1개를 이전 실행 파일과 비교했다.

- 15개 질문의 검색 결과 59건과 순서가 모두 동일했다.
- 이전에 제거한 무관한 5건은 다시 들어오지 않았다.
- 실제 두 사례에서 예상한 후속 출처 ID를 얻고 원문을 읽어 필요한 내용을 확인했다.
- 두 번째 사례는 검색에 없던 설명을 출처 ID로 읽었다. 설명에는 질문의 확장명은
  없지만 다른 일반 영문 이름은 있으므로, 이름 필터만이 누락 원인이었다고 단정하지 않는다.
  질문의 영문 이름이 전혀 없는 설명을 연결하는 동작은 별도 통제 회귀 검사에서 확인했다.
- 나머지 13개 질문에는 링크나 추가 응답 글자가 생기지 않았다.

| 직렬화 MCP 응답 글자 수 | 이전 | 후속 ID 안내 |
|---|---:|---:|
| 15개 질문 검색 응답 합계 | 40,596 | 40,860 |
| 사례 1: 검색 + 필요한 원문 읽기 | 7,856 | 3,764 |
| 사례 2: 검색 + 필요한 원문 읽기 | 9,096 | 4,953 |

링크가 붙은 검색은 각각 132자 길어졌다. 검색 전체 합계는 약 0.65% 증가했다.
반면 두 사례에서 검색 후 원문까지 읽는 합계는 각각 약 52.1%, 45.5% 감소했다.
이전에는 `memory_get(question_id, after=5, max_chars=8000)`으로 주변 기록을 읽었고,
후보에서는 `memory_get(following_id, max_chars=8000)`으로 해당 출처만 읽었다.
두 경로 모두 검색 1회와 원문 조회 1회로 호출 수는 같다.

이는 정해진 두 조회 경로의 **반환 글자 수 비교**다. 청구 토큰·비용·속도 절감률,
AI가 안내를 실제로 선택하는 빈도나 답변 정확도의 향상을 입증하지 않는다.
실제 AI를 다시 실행한 비교도 아니다. 과거 답변의 작업·시간 주장 자체를 재검증한
것이 아니라, 질문에 필요한 기록을 DB에서 읽을 수 있음을 확인했다.

회귀 검사에는 이름 없는 후속 설명, 다음 사용자 발언 경계, 다른 세션·프로젝트·
출처·작업 경로, 분류 필터, 민감 표시, 다중 조각, 삭제, 기존 결과 수와 중복,
최신순·영구 기억 조회 유지, 원문 읽기의 비밀값 가림을 포함했다.

최종 작업 소스에서 라이브러리 검사 121개와 실행 파일 검사 5개, 형식 검사,
Clippy, 배포용 빌드, pi 번들 빌드·smoke 검사와 실제 stdio MCP 검사가 통과했다.
기존의 별도 미커밋 작업은 보존했다. 위 숫자는 현재 작업 소스 검사이며, 새 커밋만
분리한 배포 검사를 뜻하지 않는다.

## v0.3.1 출시 소스 재검증

별도 미커밋 실험을 제외한 출시 소스에서는 라이브러리 검사 120개와 실행 파일 검사
5개가 통과했다. 형식 검사, Clippy, 라이선스 검사, 배포용 빌드, pi 검사와 실제
stdio MCP 검사도 통과했다. 코어 압축 파일과 확장 패키지를 풀어 실행했다.

출시 소스와 기존 설치본을 같은 시점에 다시 비교한 결과, 15개 질문의 검색 결과
59건과 순서가 같았다. 검색 응답 합계도 위 표와 같았다. 원문 조회 응답에서 별도
실험 필드가 빠져 사례 1은 3,726자, 사례 2는 4,915자였다. 과거 검사와 다른 시점에
순위가 바뀐 두 질문은 구버전에서도 같이 바뀌었다. 시간 의존 점수가 있으므로 서로
다른 시점의 순위 차이를 이번 기능의 효과로 보지 않는다.

개인 질문, 원문, 기록 ID와 검증 DB는 저장소에 포함하지 않는다.
릴리스 게시와 각 사용자의 실행 중인 설치 교체는 별개다.
