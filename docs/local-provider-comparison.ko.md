# 로컬 제품 비교

[English](local-provider-comparison.md) | [한국어](local-provider-comparison.ko.md)

이것은 작고 재현 가능한 실험이며, Memnest가 가장 좋은 기억 시스템이라는 주장이 아닙니다. 고정 자료 `scripts/fixtures/coding-memory.json`을 썼습니다. 직접 작성한 기록 16개, 그중 현재 상태 15개, 질문 48개(정답 문서가 지정된 질문 22개, 정답이 없는 질문 26개)입니다.

## 조건

네 조건 모두 실제 저장과 검색 경로를 돌렸습니다. 답하는 모델과 프롬프트는 같은 로컬 Qwen2.5:3b(Ollama 모델 digest `357c53fb659c`), temperature 0입니다. 유료 API는 부르지 않았습니다. 각 제품의 네트워크 연결은 루프백으로 제한했고, 유료 제공자 자격 증명 환경 변수는 지웠습니다.

- Memnest: 실제 HTTP 서비스, multilingual-e5-base, 하이브리드 검색, 상위 발췌 5개
- memU: 고정 소스 `2c050bc9681a4c0aff1af211a000e73d14f33356`, 0.11.0b3. 실제 `commit_results`와 `progressive_retrieve`, 로컬 BGE-M3
- Hindsight: 고정 소스 `9269b88417ed263e5a8350f2e416ca2b322756b1`, 0.10.2. 실제 `retain_async`와 `recall_async`, 로컬 Qwen 추출, 로컬 BGE-M3, PostgreSQL/pgvector, RRF 재순위. 빈 범위 질문용으로 빈 저장소를 따로 만들었습니다.
- 파일: 공개된 유니코드 토큰 교집합 기준선, 겹치는 단어가 없으면 답을 포기, 상위 5개. 일부러 단순하게 만든 것이고, 조정된 검색 제품이 아닙니다.

memU에는 미리 준비한 원문 기억 파일을 넣었습니다. 외부 에이전트로 기억을 발전시키는 단계는 시험하지 않았습니다. 모든 제품에 같은 현재 상태를 넣었으므로, 시간순 원본 대화에서 갱신과 충돌을 해결하는 능력은 재지 않았습니다. 각 제품의 내부 모델 구성은 다릅니다. Hindsight를 로컬 소형 모델로 추출한 결과를, 호스팅 버전이나 공개된 벤치마크 점수 대신 쓰면 안 됩니다.

## 결과

| 측정 | Memnest | memU | Hindsight | 파일 |
| --- | ---: | ---: | ---: | ---: |
| 끝까지 처리한 검색/답변 질문 | 48/48 | 48/48 | 48/48 | 48/48 |
| 지정 문서가 1위 | 20/22 | 22/22 | 21/22 | 17/22 |
| 지정 문서가 상위 5위 안 | 21/22 | 22/22 | 22/22 | 17/22 |
| 정답 없는 질문에서 빈 검색 결과 | 1/26 | 1/26 | 1/26 | 8/26 |
| 정답 있는 질문에서 용어 검사 통과 | 16/22 | 18/22 | 10/22 | 10/22 |
| 정답 없는 질문에서 `NOT_FOUND` 답변 | 26/26 | 26/26 | 26/26 | 26/26 |
| 검색 중앙값 | 55.2 ms | 337.5 ms | 448.6 ms | 0.089 ms |
| 검색 p95 | 86.2 ms | 698.2 ms | 733.5 ms | 0.278 ms |

용어 검사는 `scripts/compare-local-memory.py`에 있습니다. 필요한 숫자, 명령, 필드 이름이 있는지 봅니다. 의미까지 판단하는 채점이 아니어서, 다른 말로 바꾼 답은 떨어지고 불완전한 답이 통과할 수 있습니다. 문서 검색 성공이 답의 정확도는 아닙니다. 답하는 모델의 시간과 토큰은 검색 지연과 따로 봐야 합니다.

리눅스 한 대에서 순서대로 돌렸고, 캐시 상태에 영향을 받습니다. 첫 실행에서 Memnest의 기록 입력은 약 19초, memU는 약 12초, Hindsight는 약 299초 걸렸습니다. 이 설정에서 본 값일 뿐, 안정적인 비용이나 처리량 주장으로 보면 안 됩니다. 나중에 끝까지 돌린 실행의 입력 시간은 원본 결과에 따로 남아 있습니다.

첫 실행 하나는 Hindsight의 빈 저장소를 만들지 않아서 클라이언트/설정 오류가 났고, 이는 품질 결과가 아닙니다. 고친 실행은 48개 질문을 모두 마쳤습니다. 파일 기준선은 6번째 질문 뒤 900초 명령 제한에 걸렸고, 같은 자료, 모델, 프롬프트로 나머지 질문을 이어서 돌렸습니다. 원본 보고서에 이어서 돌린 사실이 적혀 있고, 끝나지 않은 행은 완료로 세지 않았습니다.

정직하게 해석하면, Memnest는 여기서 빨랐지만 지정 문서를 찾는 데서는 memU나 Hindsight를 이기지 못했습니다. 그래서 Memnest를 고를 이유는 근거 없는 정확도 주장이 아니라, 원문 기록 중심의 작업 방식과 운영 제어여야 합니다.

## 선택 기능: 로컬 근거 선택

별도 실험에서 Memnest 검색에 `evidence_only=true`를 붙였습니다. 설정된 로컬 모델이 제한된 JSON으로 원문 발췌를 고르고, 코어는 돌아온 ID와 텍스트가 실제로 넘긴 원문에 속하는지 확인했습니다.

정답 있는 질문 22개 중 20개에서 지정 답을 찾았고, 정답 없는 질문 26개 모두에서 발췌를 돌려주지 않았습니다. 일반 검색은 정답 있는 질문 21/22를 찾았지만, 정답 없는 질문에서 빈 결과를 준 것은 1개뿐이었습니다. 중앙값/p95 지연은 약 2.45/5.92초가 됐습니다. 이 비용에는 로컬 모델이 하나 더 들고, 그 모델의 메모리는 코어의 약 1.7 GB RSS에 포함되지 않습니다.

이 선택은 직접 켜야 하는 기능이며 새 기본값이 아닙니다. 모델이 고른 발췌는 검증된 사실이 아니고, 1000자 발췌 5개 안에 없다고 전체 기록에 없다는 뜻도 아닙니다. 기본 Memnest 저장과 검색은 여전히 생성 모델을 부르지 않습니다.

## 재현

고정 소스와 의존성을 갖춘 격리된 환경을 쓰세요. Qwen2.5:3b와 BGE-M3가 있는 로컬 Ollama, 그리고 일회용 로컬 PostgreSQL/pgvector를 실행합니다. 운영 기억 저장소는 쓰지 마세요.

```sh
/path/to/comparison-venv/bin/python scripts/compare-local-memory.py \
  --model-url http://127.0.0.1:<actual-model-port> \
  --postgres-url postgresql://postgres@127.0.0.1:<actual-db-port>/hindsight \
  --output /private/comparison.json
```

이 명령은 루프백 주소인지 확인하고, 자체 Memnest 임시 저장소를 만들고, 질문별 맥락, 답, 사용량, 오류를 기록합니다. 다시 돌릴 때는 실제 실행 파일 해시, 소스 리비전, 패키지 버전, 모델 digest, 호스트, 원본 결과를 기록하세요. 공개 보고서에서 개인 원본 기록으로 고정 자료를 대신하려면 별도의 개인정보 검토가 필요합니다.
