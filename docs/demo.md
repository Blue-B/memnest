# Two clients, one saved decision

<!-- markdownlint-disable MD013 -->

This demo uses two independent curl processes against Memnest's MCP endpoint. The second process receives no chat history from the first. It retrieves a decision from the shared service instead.

It exercises the same `memory_remember` and `memory_search` tools available to connected agents. It does not launch Claude Code or Codex, call an LLM, or test whether an agent chooses to use memory automatically.

## Requirements

- A running Memnest service, installed with the [quick start](../README.md#quick-start).
- curl and a POSIX shell, such as Bash on Linux or WSL.
- A local service without bearer authentication for the commands below. If authentication is enabled, add your configured bearer header to each request without putting credentials in shared logs.

The commands write one fictional decision to the dedicated `memnest-demo` project. This separates search scope, not database files: use a disposable service with its own `--data-dir` if you do not want demo data in your normal store. They do not start transcript capture or change agent settings.

The first write may download the embedding model. The requests allow up to five minutes; a slow cold download can exceed that budget. See [operations](operations.md#cli-reference) for `--warmup-embedding`.

## Client A: save a decision

Run this from a terminal. Set `MEMNEST_URL` if the service is not at the default address.

```bash
curl --fail-with-body --silent --show-error --max-time 300 \
  "${MEMNEST_URL:-http://127.0.0.1:3111}/mcp" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  --data-binary @- <<'JSON'
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"memory_remember","arguments":{"text":"Checkout webhooks: use the event ID as the idempotency key; retries must not charge twice.","project":"memnest-demo","memory_kind":"rule","importance":"decision"}}}
JSON
```

The JSON response's `result.content` contains the write result and memory ID. Check that it reports `status: succeeded`, not a JSON-RPC `error` or `isError: true`, before continuing. HTTP success alone is not tool success.

## Client B: retrieve it without the first client's history

Open another terminal and run the following command. If you set `MEMNEST_URL` above, set it to the same address in this terminal too.

```bash
curl --fail-with-body --silent --show-error --max-time 300 \
  "${MEMNEST_URL:-http://127.0.0.1:3111}/mcp" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  --data-binary @- <<'JSON'
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"memory_search","arguments":{"query":"How should checkout webhook retries avoid duplicate charges?","project":"memnest-demo","n_results":3}}}
JSON
```

The returned text should include the saved decision:

```text
Checkout webhooks: use the event ID as the idempotency key; retries must not charge twice.
```

This is an excerpt, not a complete response. IDs and scores vary. In an empty demo project, the retrieved ID should match the ID returned to Client A. A missing result or tool error means the demo has not succeeded.

## Try it with your agents

Connect both agents to that same HTTP service using the [adapter guide](../adapters/README.md#mcp-clients). Ask the first agent to call `memory_remember` with Client A's arguments. In a fresh session in the other agent, ask it to call `memory_search` with Client B's arguments.

Inspect the actual tool result rather than accepting an answer from the model's own knowledge. The saved rule is a fictional example, not a complete payment implementation.

## Remove the example

Call `memory_delete` with each memory ID returned by your demo writes. This is a soft delete: the record moves to trash, and retention is described in [operations](operations.md#retention-and-recovery). Repeated writes of structured rules may create multiple IDs, so keep each write response if you repeat the demo.
