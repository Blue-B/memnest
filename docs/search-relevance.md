# 검색 결과의 불필요한 채우기 줄이기

## 변경

한국어 질문에 영문 이름이 명시된 경우, 기존 검색 후보 중 그 이름과 맞는 기록이
있다면 이름이 전혀 없는 후보로 나머지 결과 수를 채우지 않는다.

- 기존 한국어 조사 처리와 영어 불용어 처리를 재사용한다.
- 영문 이름은 대소문자를 무시하되 단어 경계를 확인한다. 예를 들어 `pi`를
  `API`나 `pipeline` 안에서 찾았다고 인정하지 않는다. `task도`는 `task`와 맞는다.
- 반환되는 600자 발췌가 아니라 전체 기록에서 확인한다.
- 이름과 맞는 후보가 없으면 기존 의미 검색 동작을 유지한다.
- 오래됐다는 이유나 최종 점수가 음수라는 이유로 제거하지 않는다.
- 새 모델, 추가 임베딩 요청, 생성형 AI 호출과 새 의존성은 없다.

공통 검색 경로에 적용하므로 HTTP, MCP와 같은 경로를 쓰는 문맥 조회에 적용된다.
`n_results`는 최대 개수이며, 결과를 반드시 그 수만큼 채우지는 않는다.

이것은 완전한 관련성 판정이 아니다. 같은 이름을 언급하는 무관한 기록은 남을 수
있고, 이름 없이 같은 대상을 설명한 기록은 이름이 맞는 후보가 있을 때 제외될 수 있다.
한국어만 쓰거나 영어만 쓰는 검색은 이 필터로 바꾸지 않는다.

v0.3.1에서는 검색된 질문에 답변 출처 ID를 안내해, 같은 대화의 설명을
이름 없이도 읽는 경로를 보완했다. 범위와 한계는 [후속 기록 안내](following-capture.md)를
참고한다. 후속 출처 안내는 아래 이름 필터 검증과 별도로 시험했다.

## 검증

구현 전에 실제 회상 질문 2개, 기존 실기록 질문 12개와 검사할 기록을 고정했다.
격리된 같은 DB와 같은 질문으로 이전/수정 실행 파일을 각각 한 번 실행했다.
생성형 모델에 답변을 만들게 한 실험은 아니다.

| 항목 | 이전 | 수정 후 |
|---|---:|---:|
| 회상 질문에서 사전에 확인한 무관한 결과 | 5개 | 0개 |
| 두 질문의 필수 회상 시작점 유지 | 2개 | 2개 |
| 기존 12개 질문의 지정 기록이 첫 5개에 존재 | 9개 | 10개 |
| 기존에 찾았던 지정 기록 보존 | 9개 | 9개 |
| 14개 질문의 총 반환 기록 | 66개 | 54개 |
| 직렬화한 MCP 응답 글자 수 합계 | 45,431자 | 38,577자 |

응답 글자 수 합계는 **15.1% 감소**했다. 다만 네 질문은 응답이 더 길어졌다.
실제 청구 토큰, 전체 대화 비용이나 후속 원문 조회 비용의 절감률은 측정하지 않았다.

한 회상 질문은 5개 결과 대신 관련된 과거 질문 1개를 반환했다. 당시 답변은 여전히
주변 대화 조회로 읽어야 한다. 첫 검색에서 원문 답까지 자동으로 해결한 것은 아니다.
두 회상 질문은 같은 필요를 다르게 표현한 사례이며, 전체 사용자나 모든 언어의
검색 정확도를 대표하지 않는다.

회귀 검사는 `core/src/server/api.rs`에 있다. 다음을 확인한다.

- 식별자 경계와 한국어 조사 처리.
- 적합한 이름이 없을 때 의미 검색 유지.
- 공통 질문 단어만 겹친 기록으로 결과를 채우지 않음.
- 이름이 발췌 범위 뒤에 있어도 인정.
- 오래된 음수 점수 기록도 이름이 맞으면 유지.

push할 변경만 따로 추출한 소스에서도 라이브러리 검사 119개, 실행 파일 검사 5개와
배포용 빌드가 통과했다. 그 실행 파일로 위 14개 질문의 결과 목록과 응답 길이가
같음을 확인했고, 실제 CLI 가져오기 및 삭제·재시작·색인 재구성 검사도 통과했다.

개인 질문, 대화 원문, 기록 ID, 인증 정보와 검증 DB는 저장소에 포함하지 않는다.

## 2026-11-10: 자동 회상 주제 게이트와 다른 프로젝트 안내

두 가지를 바꿨다. 둘 다 기본 동작이고 끄는 설정은 없다.

1. **자동 회상 게이트.** `memnest hook`이 쓰는 `/context`는 프롬프트와 주제가 같은
   기억만 넣는다. 직접 하는 검색(`memory_search`, `/search`)은 그대로다.
2. **다른 프로젝트 안내.** `project` 없이 작업공간 범위로 검색했는데 다른 프로젝트에
   확실히 더 잘 맞는 저장 기억이 있으면, 결과 끝에 그 프로젝트 이름을 알리는 한 줄을
   붙인다. 검색 범위는 넓히지 않는다.

### 측정 방법

- 2026-11-10의 실제 저장소 복사본(기록 54,734개)을 임시 폴더에 복원해 썼다. 원본
  저장소와 실행 중인 서비스는 건드리지 않았고, 복사본은 측정 뒤 지웠다.
- 프롬프트 47개. 실제 사용자 프롬프트 3,560개에서 고정 시드로 150개를 뽑고, 그중
  프로젝트나 주제를 지목한 구체적인 질문 22개와 "계속해", "왜 그래" 같은 모호한
  후속 말 22개를 골랐다. 여기에 문제로 보고된 사례 3개(구체적 1개, 모호한 2개)를
  더했다. 구체적 23개, 모호한 24개다.
- 모든 요청은 실제 사용과 같은 작업 폴더로, `project` 없이 보냈다.
- 비교 대상은 배포된 0.5.1이다. 0.5.1이 넣은 기억 117개를 새 빌드를 만들기 전에
  하나씩 읽고 관련(질문에 답하거나 직접 다룸), 약한 관련(같은 대상이지만 질문과
  다른 내용), 무관으로 나눴다. 새 빌드에서 처음 나온 8개는 나중에 같은 기준으로
  나눴다. 판정은 한 사람이 했고, 이 8개는 어느 빌드의 결과인지 알고 판정했다.

### 게이트를 점수로 만들지 않은 이유

최종 점수에는 나이, 기록 종류, 중요도가 섞여 있다. 0.5.1이 넣은 관련 기억 12개의
점수는 −0.159에서 0.210 사이였고, 무관한 기억의 점수는 −0.178에서 0.237 사이였다.
pi 확장의 자동 문맥이 쓰는 기준(점수 0.25 이상)을 그대로 쓰면 관련 기억 12개가
모두 빠진다. 그래서 두 검색기가 내는 원래 신호만 썼다.

- 임베딩 거리만으로는 가를 수 없었다. 이 모델(multilingual-e5-base)의 거리는 폭이
  좁다. 관련 기억은 0.109~0.156, 무관한 기억은 0.121~0.245였다.
- 키워드 일치만으로도 가를 수 없었다. 무관한 기억이 걸린 이유는 대부분 "그러면",
  "지금", "저거" 같은 말이 겹쳐서였다.

### 정한 규칙

프롬프트에서 주제어를 뽑는다. 기존 키워드 추출에서 대화용 말 73개(한국어 47개,
영어 26개)를 뺀 것이다. 기억 전체 글에서 주제어를 찾고, 영문 주제어는 단어 경계를
확인한다. 다음 중 하나면 남긴다.

| 조건 | 임베딩 거리 한도 |
|---|---:|
| 주제어 2개 이상이 기억에 있음 | 0.18 |
| 주제어 1개가 기억에 있음 | 0.13 |
| 기억이 다른 언어(한글이 있는지 없는지)이고 프롬프트에 주제어가 2개 이상 | 0.21 |

시도한 순서는 이렇다.

| 시도 | 관련 기억 유지 | 아무것도 안 넣은 모호한 프롬프트 | 비고 |
|---|---:|---:|---|
| 주제어 2개와 0.18, 다른 언어 0.23, 대화용 말 제외 없음 | 11/12 | 24/24 | 대화용 말 2개가 겹친 무관한 기억이 남음 |
| 위에 대화용 말 제외 추가 | 10/12 | 24/24 | 주제어가 1개뿐인 관련 기억 2개가 빠짐 |
| 위에 "주제어 1개와 0.13" 추가 | 12/12 | 24/24 | |
| 다른 언어 한도를 0.21로, 프롬프트 주제어 2개 이상일 때만 | 12/12 | 24/24 | 최종. 모호한 한국어 프롬프트가 대화용 말뿐인 영어 기억(거리 0.176)을 넣는 것을 시험에서 발견해 막음 |

### 결과

| 항목 | 0.5.1 | 변경 후 |
|---|---:|---:|
| 넣은 기억 합계 (47개 프롬프트) | 117개 | 30개 |
| 무관한 기억 | 95개 (프롬프트당 2.0개) | 14개 (프롬프트당 0.3개) |
| 약한 관련 기억 | 10개 | 4개 |
| 관련 기억 | 12개 | 12개 |
| 아무것도 넣지 않은 모호한 프롬프트 | 24개 중 4개 | 24개 중 24개 |
| 아무것도 넣지 않은 구체적 프롬프트 | 23개 중 0개 | 23개 중 9개 |

아무것도 넣지 않게 된 구체적 프롬프트 9개는 0.5.1에서도 관련 기억이 없었다(무관
25개, 약한 관련 2개). 통과한 기억이 없으면 `memnest hook`은 빈 묶음도 붙이지 않는다.

### 다른 프로젝트 안내 규칙

작업공간 범위 검색 뒤에, 호출자가 읽을 수 있는 전체 프로젝트를 한 번 더 찾는다.
질문 임베딩은 다시 만들지 않고 첫 검색의 것을 쓴다. 저장 기억(대화 기록 제외)
상위 10개 중에서 다음을 모두 만족하는 것을 센다.

- 위 게이트를 통과한다.
- 점수가 범위 안 결과 중 게이트를 통과한 것의 최고 점수보다 0.05 넘게 높다. 범위
  안에 통과한 결과가 없으면 통과한 것 모두를 센다.
- 휴지통, 대체된 기록, 작업 카드, `root`/`default`/`global`, 민감 기록이 아니다.
  권한 정책으로 읽을 프로젝트가 제한된 호출자에게는 안내를 만들지 않는다(허용된
  프로젝트 전체를 검색마다 읽게 되기 때문이다). 최신순 검색에도 만들지 않는다.
- 프로젝트 이름이 글자, 숫자, `-`, `_`, `.`, `/`로만 된 80자 이하 이름이다.

안내에는 프로젝트 이름(최대 3개)과 개수만 들어가고 기억 내용은 들어가지 않는다.
호출자가 `project`를 지정했으면 붙지 않는다.

47개 프롬프트 중 범위 밖에 게이트를 통과한 기억이 있던 것은 6개였고 모두 구체적
프롬프트였다. 범위 밖 최고 점수에서 범위 안 최고 점수를 뺀 값은 안내가 나온 3개에서
+0.065, +0.101, +0.292였고, 나오지 않은 3개에서 −0.093, −0.137, −0.248이었다. 기준
0.05는 이 두 묶음 사이에 있다. 표본이 6개뿐이라 기준이 정밀하게 정해진 것은 아니다.

- 안내가 나온 3개는 모두 프롬프트가 다루는 프로젝트를 가리켰다. 보고된 사례 1개는
  세어진 기억이 바로 찾던 결정이었다. 나머지 2개는 맞는 프로젝트였지만 세어진
  기억(각 1개)은 질문에 직접 답하지 않았다.
- 모호한 프롬프트 24개에서는 한 번도 나오지 않았다.
- 놓친 것 2개를 찾았다. 하나는 경로 이름 프로젝트에 같은 대상을 다룬 기억이 있었지만
  게이트를 통과하지 못했다(범위 안에 이미 관련 기억 3개가 있었다). 다른 하나는
  모호한 프롬프트의 문구를 그대로 인용한 다른 프로젝트 기억으로, 주제어가 1개뿐이라
  통과하지 못했다. `project="all"` 직접 검색으로는 둘 다 찾는다.

### 지연 시간

세 서버(0.5.1, 변경 직전 브랜치, 변경 후)를 같은 복사본으로 띄우고 47개 프롬프트를
순서를 바꿔 가며 3번씩 차례로 보냈다(서버당 141회). 측정 중 1분 부하 평균은
8.5~12였다.

| | `/context` p50 / p95 | `/search` p50 / p95 |
|---|---:|---:|
| 0.5.1 | 997 / 1697 ms | 978 / 1760 ms |
| 변경 직전 브랜치 | 777 / 1357 ms | 758 / 1482 ms |
| 변경 후 | 702 / 1281 ms | 711 / 1199 ms |

같은 프롬프트끼리 짝지은 차이(변경 후 − 변경 직전)의 중앙값은 `/context` −15 ms,
`/search` −12 ms였고 사분위 범위는 각각 −78~+50 ms, −161~+37 ms였다. 이 부하에서는
추가 비용이 잡음보다 작아 따로 드러나지 않았다. 두 번째 검색과 같은 일을 하는 전체
범위 저장 기억 검색(10개, 임베딩 포함)은 p50 17 ms, p95 37 ms였다(94회).

### 이전 결정과의 관계

- 이 문서 앞부분의 이름 필터는 그대로다. 직접 검색은 오래됐거나 점수가 음수라는
  이유로 결과를 빼지 않는다. 새 게이트도 나이와 최종 점수를 쓰지 않으며 자동
  회상에만 적용된다.
- 새 모델, 생성형 AI 호출, 새 의존성은 없다. 임베딩 요청도 늘지 않았다.
- pi 확장의 자동 문맥(`autocontext.ts`, 점수 0.25 이상)은 `/search`를 쓰므로 바뀌지
  않았다. 그 기준은 더 엄격하고 그대로 유지된다.
- [짧은 검색과 원문 읽기](bounded-retrieval.md)의 응답 형식은 그대로이고, 안내 한
  줄만 선택적으로 붙는다.
- [2026-10-06 회상 점검](recall-check-2026-10-06.md)은 `project=all` 직접 검색을
  다뤘고 그 경로는 바뀌지 않았다.

### 한계

- 판정은 한 사람이 한 저장소, 47개 프롬프트로 했다. 한국어 사용자 한 명의 기록이며
  다른 사용자나 언어를 대표하지 않는다.
- 남은 무관한 기억 14개 중 6개는 0.5.1에서는 없던 것이다. 약한 관련 기억이 빠진
  자리에 주제어가 겹친 무관한 기억이 들어왔다. 프롬프트 1개에서는 약한 관련 3개가
  무관한 3개로 바뀌었다.
- 다른 언어 기억은 거리로만 판단한다. 만든 한·영 시험 쌍 8개 중 4개(거리
  0.159~0.209)만 한도 안에 들고 4개(0.248~0.275)는 빠진다. 무관한 다른 언어 기억이
  0.237부터 시작해 한도를 더 올릴 수 없었다. 빠진 쌍도 직접 검색으로는 찾는다.
- 같은 이유로, 모호한 프롬프트라도 대화용 말이 아닌 낱말이 2개 이상이면("해야",
  "해봐" 같은 동사도 센다) 다른 언어로 쓰인 대화체 기억이 한도 안에 들어올 수 있다.
  만든 시험에서 그런 쌍의 거리는 0.176~0.214였다. 실제 저장소의 모호한 프롬프트
  24개에서는 일어나지 않았다.
- 주제어가 하나뿐인 프롬프트("그럼 바이오스는 어떻게?")에는 다른 언어로 쓰인 기억이
  들어오지 않는다. 다른 언어 규칙은 주제어 2개를 요구하기 때문이다. 0.5.1은 이
  경우 영어 기억을 넣었다. 직접 검색으로는 찾는다.
- 접근 정책으로 읽을 프로젝트가 제한된 호출자와 최신순 검색에는 다른 프로젝트
  안내가 나오지 않는다.
- 대화용 말 목록은 한국어와 영어뿐이다.
- 거리 한도는 이 임베딩 모델에 맞춘 값이다. 모델을 바꾸면 다시 정해야 한다.
- 안내는 "더 높은 점수의 주제가 같은 기억이 있다"는 뜻이지 "답이 있다"는 뜻이
  아니다.
