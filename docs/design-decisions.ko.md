# 설계 결정

<!-- markdownlint-disable MD013 -->

[English](design-decisions.md) | [한국어](design-decisions.ko.md)

memnest가 지금 모양으로 만들어진 이유입니다. 요청 경로 밖에 남아 있는 실험이 아니라, 실제로 배포되는 구조를 다룹니다.

## 임베딩은 로컬에서 돌립니다

저장소에는 결정, 정정, 대화 기록이 들어 있습니다. 모든 기억과 질문을 호스팅 임베딩 API로 보내면 로컬 우선이라는 경계와 맞지 않습니다.

Rust 엔진은 `fastembed`로 ONNX 모델을 프로세스 안에서 돌리며, 별도의 Python 프로세스가 필요 없습니다. 임베딩이 처음 필요한 작업 때 선택한 모델을 내려받습니다. `memnest --warmup-embedding`으로 서비스 시작 전에 미리 받아 둘 수 있습니다.

## 기본 모델은 multilingual-e5-base

한 프로젝트 안에서도 여러 언어가 섞일 수 있으므로 기본 모델은 다국어여야 합니다. 프롬프트 시점 회상은 지연 시간 여유가 짧고, 편집기, 브라우저, 코딩 에이전트와 함께 돌아갑니다. `intfloat/multilingual-e5-base`는 모델 크기, 벡터 크기, 다국어 검색 품질 사이의 중간 선택입니다.

모델은 바꿀 수 있습니다.

```bash
MEMNEST_EMBED_MODEL=BAAI/bge-m3
MEMNEST_EMBED_DIM=1024
```

기존 벡터는 이전 차원을 쓰므로, 모델을 바꾸면 벡터 색인을 다시 만들어야 합니다.

## 키워드 검색과 벡터 검색은 따로 둡니다

BM25는 포트 번호나 crate 이름 같은 정확한 단어를 찾지만, 다른 말로 바꾼 표현은 놓칠 수 있습니다. 벡터 유사도는 바꾼 표현을 찾지만, 원래 단어에서 벗어날 수 있습니다. 어느 쪽이 중요한지는 질문이 정하는데, 기억을 저장할 때는 질문을 알 수 없으므로 모든 기억을 두 방식으로 색인합니다.

두 검색의 점수는 서로 비교할 수 없습니다. 그래서 BM25 점수와 벡터 거리를 더하지 않고, Reciprocal Rank Fusion으로 순위를 합칩니다. 합친 뒤 MMR을 돌려서 거의 같은 기억이 결과를 채우지 않게 합니다.

어떤 검색 방식도 저장소에 답이 있다는 것을 증명하지 않습니다. 호출하는 쪽은 돌아온 기억을 확인할 후보로 다뤄야 합니다.

## SQLite가 원본입니다

SQLite에 모든 원래 기록이 있습니다. Tantivy와 HNSW는 다시 만들 수 있는 파생 색인입니다.

기억 행과 그 `index_queue` 작업은 하나의 트랜잭션으로 씁니다. 작업은 두 색인이 모두 안전하게 기록된 뒤에만 지웁니다. 중간에 멈춰도 다음 시작 때 끝내거나 다시 만들 정보가 남습니다.

한 데이터 폴더에는 한 프로세스만 쓸 수 있습니다. 두 번째로 쓰려는 프로세스는 SQLite와 색인을 두고 경쟁하지 않고 거부됩니다.

## 작업공간 범위는 경로 해시를 씁니다

기억은 작업 폴더별로 나뉘지만, 공개되는 작업공간 ID는 정규화한 절대 경로의 고정 해시입니다. 그래서 이름이 같은 두 폴더가 섞이지 않고, 전체 로컬 경로도 드러나지 않습니다.

추론된 검색은 현재 작업공간과 `playbook`을 함께 찾습니다. 여러 프로젝트를 찾으려면 `project=all`이 필요합니다.

## 정정은 이력을 남깁니다

오래된 기억은 새 값을 `supersedes=<id>`로 저장해 대체합니다. 두 변경은 하나의 SQLite 트랜잭션으로 처리되고, 이전 행은 숨겨진 `_superseded` 컬렉션으로 옮겨집니다.

Memnest는 소스 코드를 읽지 않으며, 저장된 내용이 틀려졌는지 판단할 수 없습니다. 변화를 본 쪽이 정정을 써야 합니다.

## 비밀값은 검색 대상 기억과 분리합니다

키워드와 벡터 색인이 읽어야 하므로 일반 기억 텍스트는 암호화하지 않고 저장합니다. 자격 증명처럼 보이는 문자열은 저장 전에 가리지만, 패턴으로 모든 비밀을 잡을 수는 없습니다.

자격 증명은 AES-256-GCM 금고에 넣어야 합니다. 모델이 쓰는 금고 도구는 믿을 수 있는 프로세스에 `MEMNEST_EXPOSE_SECRET_TOOLS=1`을 설정하지 않는 한 숨겨져 있습니다.

## 프롬프트 훅은 실패해도 막지 않습니다

`memnest hook`은 사용자가 프롬프트를 보내는 동안 실행됩니다. 서비스가 없거나, 작업공간을 모르거나, 다른 오류가 나면 아무것도 출력하지 않고 성공으로 끝납니다. 기억 회상 때문에 에이전트를 쓰지 못하면 안 되기 때문입니다.

가져온 내용은 믿을 수 없는 참고 자료라고 표시하고, 안에 든 마크업은 넣기 전에 이스케이프합니다.

## 대화 수집은 수집기 하나로 합니다

MCP는 도구 호출만 보여 주고 호스트의 대화 이벤트는 보여 주지 않습니다. 그래서 `memnest watch`가 pi, Claude Code, Codex가 이미 쓰고 있는 대화 기록 파일을 읽습니다.

수집기는 보이는 사용자와 어시스턴트 텍스트를 저장하고, 시스템 프롬프트, 추론, 도구 입출력, 이미지, 하위 에이전트 대화는 건너뜁니다. 수집 경로가 하나면 호스트마다 확장을 따로 두는 것보다 작고 점검하기 쉽습니다.

## 기본으로 LLM 정리기를 두지 않습니다

원본 대화 기록은 명시적 검색에서 그대로 찾을 수 있습니다. 자동 맥락에는 일부러 저장한 수동 기억과 정리된 기억만 넣어서, 검토하지 않은 대화가 조용히 프롬프트 지침이 되지 않게 합니다.

저장소에 있는 한국어 질문 3개짜리 검색 점검은 생성 모델 없이 지정한 대화를 모두 찾았습니다. 일반적인 검색 품질을 말하기에는 너무 작고, MemoryBench 전체 답변과 채점은 여전히 외부 모델 자격 증명과 비용이 필요합니다. 이 증거만으로는 요약 모델, 제공자 설정, 또 다른 손실 있는 저장 경로를 더할 이유가 되지 않습니다.

정리기는 나중에 해 볼 수 있는 실험이며, 숨은 필수 요소가 아닙니다. 원본 검색이 중요한 코딩 결정을 놓친다는 것이 반복 가능한 벤치마크로 확인될 때만 고려합니다. 어떤 형태든 선택 기능이어야 하고, 수집 뒤에 돌고, 출처 ID를 유지하고, 검토할 수 있는 정리 기록을 쓰고, LLM 없는 기본 경로는 그대로 둬야 합니다.

작업 카드는 이 원칙의 예외가 아닙니다. 카드는 작업 중인 AI가 직접 쓰는 별도 인계 문서이고, 대화 원문은 그대로 남습니다. 자세한 내용은 [작업 카드](task-cards.ko.md)를 참고하세요.
