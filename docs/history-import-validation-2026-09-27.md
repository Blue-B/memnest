# 과거 기록 가져오기 검증 결과

이 문서는 과거 기록 가져오기 수정 단계의 결과다. 이후 적용한 검색 결과 필터와
push 직전 최종 소스 검증은 [검색 보완 결과](search-relevance.md)에 별도로 기록했다.

## 결론

**선택한 과거 파일을 다시 가져오지 못하던 문제는 수정했다. 막연한 질문의 첫 검색이 좋아졌다는 결과는 얻지 못했다.**

운영 DB, 설치된 실행 파일, 실행 중인 서비스에는 이 변경을 적용하지 않았다.
실제 자료 검증은 기존 활성 기억 25,906건의 격리 복사본에서 수행했다.

## 계획과 채택한 변경

[구현·검증 계획](history-import.md)은 검색 순위보다 확인된 수집 문제를 먼저 다룬다.

- `watch --backfill --once`가 기존 읽기 위치와 관계없이 명시적으로 선택한 원본을 처리한다.
- `--path`는 절대 경로로 지정해야 한다. 실행 중인 감시 상태는 읽거나 쓰지 않는다.
- `--dry-run`은 서버에 요청하지 않고 수집 가능한 기록 수를 보여준다. DB 누락 수는 아니다.
- 한 번의 읽기 한도를 넘어도 처음에 정한 완성된 줄의 끝까지 처리한다.
- 기존 저장 API, 기록 ID, 중복 처리와 삭제 표식을 재사용한다.
- 새 저장과 기존/삭제로 건너뛴 건수를 구분한다. 전송 실패는 실패 종료로 알린다.
- 감시가 실행 중이라는 표시가 과거 기록의 완전한 수집을 뜻하지 않음을 상태 출력에 명시했다.

검색 순위, 임베딩 모델, DB 구조와 별도 생성형 LLM은 변경하지 않았다.

## 실제 기록 전후 결과

검증 대상은 과거 작업 관리 도구를 교체한 대화 한 건이다. 로컬 원문은 있지만
검증용 DB에는 해당 대화가 없었다. 왜 과거에 빠졌는지, 처음에 건너뛴 것인지
나중에 삭제된 것인지는 이번 검사로 확정하지 않는다.

| 검사 | 결과 |
|---|---|
| 기존 실행 파일, 파일 끝을 가리키는 감시 상태에서 다시 가져오기 | 0건 |
| 수정본 미리보기 | 수집 가능한 기록 조각 42개 |
| 수정본 가져오기 | 새 저장 42개 |
| 같은 원본 재실행 | 추가 저장 0개 |
| 원본 파일과 테스트 감시 상태 | 바이트 내용 불변 |
| 미리 정한 두 질문에서 원문이 첫 5개에 등장 | **0/2, 목표 미달** |

두 질문은 같은 회상 요구의 표현만 달리한 것이며, 독립된 두 업무나 대표 표본이 아니다.
첫 질문은 나중에 작성된 수동 정리 기억이 계속 1위였다. 두 번째는 과거 질문 자체가
1위였다. 이 수동 정리 기억과 과거 질문을 원문 복구의 성과로 세지 않았다.

### DB 안에서 원문까지 읽는 경로

첫 검색 목표가 실패한 뒤, 기존 도구로 이어 찾는 경로를 별도로 확인했다.
이를 최초 질문의 성공이나 검색 품질 향상으로 바꾸어 계산하지 않는다.

1. 과거 질문을 찾은 뒤 `memory_get(after=5)`로 이어지는 당시 답변을 읽었다.
   질문을 포함해 3,025자를 받았고, 잘림 없이 교체 이력 답변을 확인했다.
   이 답변은 기존 DB에 있던 후대의 조사 결과다.
2. 기존 수동 기억에서 얻은 패키지 이름으로 다시 검색하니, 새로 가져온 원문이
   2위와 3위에 나왔다. 원본 파일 검색으로 얻은 비공개 정답 키워드를 새로 넣은 것은 아니다.
3. 그 검색 결과에 `memory_get(after=5)`를 사용해 비교 내용과 교체 이유를
   4,002자로 읽었다. 또 다른 결과를 조회해 후속 설정 교체 보고 755자를 읽었다.
   모두 잘림이 없었다. 당시 실행 확인이 아직 남았다는 제한도 원문에 포함되어 있었다.

따라서 이 사례에서 **세션 파일을 다시 열지 않고 DB 검색과 조회만으로 원문에
도달하는 경로**는 확인했다. 다만 사람이 검색어를 구체화한 검사이며, AI가 매번
이를 자동 수행한다는 보장이나 시간·토큰 절약 측정은 아니다.

## 안전성 및 실행 검사

- 수집 단위 검사 22개: 여러 읽기 구간, 미완성 마지막 줄, 미리보기의 HTTP 요청 0회,
  API 실패, 기존 ID 재시도, 원문 분할·가림 처리, 기존 감시 동작을 확인했다.
- 실제 CLI와 격리 HTTP 검사: 기존 프로그램의 누락 재현, 새 기록 2개 저장,
  재실행 추가 0개, 삭제한 기억 미복원, 감시 상태 불변을 확인했다.
- 기존 전체 수명주기 검사: 실제 휴지통 정리, 서버 재시작과 색인 재구성 후에도
  삭제한 대화가 다시 저장되지 않았다.
- 작업 중 라이브러리 전체 검사 120개와 실행 파일 검사 5개가 통과했다.
  이 수에는 아래에서 제거한 검색 실험 검사 2개가 포함된다.
- 검색 실험을 제거한 최종 소스에서는 관련 검사 29개, 배포용 빌드,
  실제 CLI 회귀와 DB 원문 조회를 다시 확인했다. 최종 소스 전체 검사를 재실행했다고
  주장하지 않는다.
- Rust 포맷, 작업 중 Clippy, Python 문법·Ruff, 셸 문법과 diff 공백 검사를 확인했다.
  기존 `transcript-e2e.sh`는 상태 초기화가 필요 없도록 갱신하고 문법만 검사했다.
  해당 동작의 실제 실행은 위 CLI/HTTP 검사에서 수행했다.
- 기존 작업 중 이번 범위 밖의 파일 21개는 시작 백업과 바이트가 같음을 확인했다.

## 채택하지 않은 검색 변경과 실패 기록

영문 이름에 한국어 조사가 붙은 검색어를 문자 검색에서도 처리하는 후보를 시험했다.
작은 독립 검사에서는 후보 누락을 재현하고 고칠 수 있었지만, 실제 두 질문에는
개선이 없었다. 원형을 대체한 첫 시도는 기존 관련 질문까지 놓쳤다. 원형도 함께
찾도록 고친 뒤에도 실제 결과는 개선되지 않았다. **두 검색 소스 파일을 원복했고,
후보 패치와 실행 파일은 비공개 검증 자료에만 보존했다.**

큰 DB를 디버그 실행 파일로 시작한 첫 검사는 준비 시간 180초를 넘겨 중단됐다.
이후 배포용 실행 파일로 같은 자료와 질문을 검사했다. 질문이나 정답을 바꾸거나
생성형 모델을 반복 실행한 것은 아니다.

## 남은 한계

- 전체 로컬 파일의 DB 포함 여부를 자동 감사하는 기능은 아니다.
- 경로 이동·별칭·내용 재작성과 과거의 다른 ID 생성 방식까지 삭제 의도를 보존하는
  마이그레이션은 구현하지 않았다. 같은 현재 ID에 대한 삭제 보호를 검증한 것이다.
- 실제 자료 복사본은 활성 기록과 작업공간만 가져왔다. 운영 DB의 전체 삭제 이력을
  복제한 실험이 아니므로, 42건을 운영 DB에 그대로 넣어도 된다는 승인이나 증거가 아니다.
- 처음 정한 넓은 검색의 원문 회수 목표는 미달이다. 올바른 수동 기억을 밀어내도록
  특정 사례에 맞춰 순위를 조정하지 않았다.
- 경쟁 제품과 같은 업무를 실행해 비교하지 않았다. 회상 정확도, 속도, 총비용의
  우위를 주장할 수 없다.

구현 위치는 `core/src/watch.rs`, `core/src/main.rs`이며,
재실행 가능한 검사는 `scripts/test-history-import.py`에 있다.
개인 대화, 질문 원문, 기록 ID와 인증 정보는 이 문서에 싣지 않았다.
