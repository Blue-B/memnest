# 과거 기록 직접 가져오기

[English](history-import.md) | [한국어](history-import.ko.md)

## 문제와 구현 계획

일반 수집기(watcher)는 새로 발견한 파일을 끝에서부터 따라갑니다. 그래서 추적 중인 파일의 위치 표시(cursor)가 있다고 해서, 그 앞의 대화가 저장됐다는 증거는 **아닙니다**. 예전에는 `watch --backfill --once`가 그 위치 표시를 그대로 써서, 과거 앞부분을 가져오지 않고도 성공으로 끝날 수 있었습니다. 또 파일에 기록이 더 있어도 정해진 읽기 한 번 뒤에 멈췄습니다.

연속 수집은 그대로 둡니다. 명시적인 일회성 가져오기는 위치 표시와 무관하게 동작하게 하고, 기존 파서, 가리기(redaction), 이벤트 식별, `/add`, 색인, 삭제 표시를 그대로 씁니다. 새 기억 구조, 순위 알고리즘, 의존성, 생성 모델은 필요 없습니다.

## 미리 보고 가져오기

수집 때 쓴 **원래 절대 경로 그대로** 쓰세요. 옮긴 사본이나 다른 표기 경로는 안 됩니다.

```sh
memnest watch --path /absolute/path/session.jsonl --backfill --once --dry-run
memnest watch --path /absolute/path/session.jsonl --backfill --once
```

일회성 재생에는 `--path`가 필수입니다. 폴더를 지정하면 그 안의 JSONL 파일을 하위 폴더까지 모두 고릅니다. 여러 경로는 옵션을 반복해서 지정합니다. 미리 보기는 HTTP 요청을 보내지 않고 수집 상태도 만들지 않습니다. 두 모드 모두 실행 중인 수집기의 `watch-state.json`을 읽거나 쓰지 않으므로, 가져오기가 위치 표시를 되감거나 덮어쓰지 않습니다. 고른 경로가 없거나 읽을 수 없으면 조용히 성공했다고 하지 않고 실패합니다.

JSON 보고서에는 다음이 들어 있습니다.

- 파일별 `eligible_turns`와 `eligible_chunks`: 기존 파서가 받아들인, 보이는 대화 텍스트. 가리기와 조각 나누기 뒤의 값입니다.
- `new_chunks`: 이번 가져오기에서 서비스가 새로 받아들인 조각
- `skipped_chunks`: 이미 알고 있거나 삭제된 이벤트 ID라서 건너뛴 조각
- `scanned_bytes`: 이번 실행 시작 때 정한, 완전한 줄까지의 범위

**대상이라고 해서 빠진 것은 아닙니다.** 미리 보기는 DB에 이미 있는지 확인하지 않습니다. 건너뛰었다고 보인다는 뜻도 아닙니다. 삭제된 기록은 일부러 되살리지 않습니다. `status`는 수집기 활동을 보여 줄 뿐, 과거 기록이 다 들어왔는지를 보여 주지 않습니다.

일회성 가져오기는 4 MiB 한 번 읽고 멈추지 않고, 고른 완전한 앞부분을 모두 처리할 때까지 정해진 크기로 나눠 읽습니다. 끝나지 않은 마지막 줄과 나중에 추가된 내용은 다음 수집이나 재생의 몫입니다. 서비스나 파일 읽기에 실패하면 0이 아닌 코드로 끝나며, 앞 조각은 이미 저장됐을 수 있습니다. 같은 원본을 처음부터 다시 시도하세요. 이벤트 ID가 고정돼 있어서 다시 해도 중복되지 않습니다.

## 경계

- 일반 `watch`와 연속 `watch --backfill`은 기존 동작 그대로입니다. 연속 `watch --backfill`은 **새로 발견한** 파일을 처음부터 읽고 추적 중인 파일은 이어서 읽습니다. 처음부터 완전히 다시 넣으려면 `--once --backfill`을 쓰세요.
- 모든 과거 파일을 자동으로 가져오는 기능이 아닙니다. 원본과 서비스(`--url`, 또는 기존 서비스 주소 기본값)는 운영자가 고릅니다.
- 사용자와 어시스턴트의 보이는 텍스트만 수집합니다. 도구 입출력, 추론, 시스템 프롬프트, 이미지, 제외된 곁가지 대화는 수집하지 않습니다. 잘못되었거나 너무 큰 줄에 대한 기존 경고도 그대로 적용됩니다. 보고서가 JSONL의 모든 바이트를 저장했다는 증거는 아닙니다.
- 기존 ID는 원본 경로, 바이트 위치, 프로젝트, 조각 순서에 따라 정해집니다. 원본을 옮기거나, 다른 이름으로 가리키거나, 다시 쓰면 ID가 바뀔 수 있습니다. 삭제한 기록을 사본이나 다른 경로 표기로 다시 넣지 마세요. 이 변경은 예전 상대 경로 ID를 옮기거나, 사본 간 중복 제거를 약속하지 않습니다.
- 서비스의 기존 삭제/삭제 표시 기능이 필요합니다. 호환되지 않는 예전 서비스로 가져오면 삭제 안전을 보장하지 않습니다.
- 가져온 시각은 원래 사건 시각이 아닙니다. 날짜를 추정하거나 옛 어시스턴트의 주장을 검증하지 않고, 검색 순위도 바꾸지 않습니다.

## 검증 계획

1. 단위 검사: 미리 보기는 HTTP를 부르지 않음. 재생이 여러 번에 나눠 읽음. 끝나지 않은 마지막 줄은 미룸. API 실패는 실행을 실패로 처리. 보고서가 새로 받은 조각과 건너뛴 조각을 구분. 명시적 경로 필수.
2. 실제 CLI/HTTP 회귀: 먼저 일반 watch가 고정 자료의 과거를 건너뛰게 하고, 예전 실행 파일의 효과 없는 backfill을 재현한 뒤, 미리 보고 가져옵니다. 상태와 원본이 바뀌지 않고, 검색이 맞고, 재생해도 중복 행이 없고, 삭제 뒤 되살아나지 않아야 합니다.
3. 기존 수명 주기 회귀: 실제 예약된 휴지통 정리, 서비스 재시작, 색인 재구축 뒤에도 삭제한 기록이 backfill로 되살아나지 않는지 확인합니다.
4. 실제 기록 확인: 활성 기억과 작업공간 범위만 격리된 개인 DB로 복사합니다. 실행 전에 빠진 원본과 회상 질문을 고정합니다. 파서 대상 조각이 모두 들어가고, 원본과 위치 표시가 바뀌지 않고, 재생 때 추가 행이 0이고, 고른 질문마다 원래 원본이 상위 5위 안에 나와야 하며, 이어서 `memory_get`으로 근거를 확인합니다.
5. 스냅샷에 이미 있는, 나중에 사람이 정리한 답은 그대로 두고, 그 답이 검색된 것을 빠진 원본을 되찾은 것으로 세지 않습니다. 답변 모델 정확도, 속도 우위, 경쟁 제품보다 낫다는 주장은 하지 않습니다.

```sh
cargo test --offline --manifest-path core/Cargo.toml --lib watch::tests
cargo test --offline --manifest-path core/Cargo.toml --bin memnest history_preview
cargo build --offline --manifest-path core/Cargo.toml
python3 scripts/test-history-import.py --old /absolute/path/to/pre-change/memnest
python3 scripts/test-memory-lifecycle.py
```

기록 검사 스크립트는 선택적으로 `snapshot`, `transcript`, `session_id`, `queries`가 든 `--case <private.json>`을 받습니다. 오프라인 모델 캐시를 쓰는, 임의 포트의 인증된 루프백 서비스에만 가져오고, 금고는 복사하지 않은 채 개인 결과물을 남깁니다. 서버는 `finally`에서 멈춥니다.

첫 검색 회상 기준을 못 맞춘 점과 기각한 검색 실험을 포함한 [기록된 검증 결과](history-import-validation-2026-09-27.md)(영문)를 참고하세요.
